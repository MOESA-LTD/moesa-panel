# M21 Cross-Tenant Transfer (Kiracılar arası veri aktarımı): Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A user entitled in two tenants rehearses, then copies or moves a customer package (or selected products of one customer) from one tenant to the other in one database transaction. Afterwards the app copies the package's Storage files and records whether the copy finished.

**Architecture:**
- **Registry.** `private.transfer_registry` (a SQL table) lists every transferred table with its root, the registry table and column that scope its rows, the polymorphic `document_entity` value it answers to, its late (cyclic) columns, user columns, code kind and insert order. The function is generic over it: each row is read as `jsonb`, its ids are rewritten through an id map, and it is written back with `jsonb_populate_record` into the non-generated columns. A pgTAP test fails when a table with a foreign key to a registry table is not registered.
- **Transfer flag.** `private.transferring()` is TRUE only while `moesa.transfer_id` names the `public.transfer` row inserted by the current transaction (`xact_id = pg_current_xact_id_if_assigned()`). A user cannot insert that row: authenticated has only SELECT on `public.transfer`. `private.rules_bypassed()` also accepts the flag. Under it, the trigger functions that would overwrite copied values, or refuse frozen rows, return at once; the integrity checks stay on. Because the gate guard is skipped, the function validates gate order and status itself.
- **One entry point.** `public.transfer_customer(...)` (SECURITY DEFINER) checks access and plans, collects the package into temp tables, validates the gates, and builds the report and its hash. With `dry_run` it returns the report. Otherwise it recomputes the report, compares the hash and the decisions, then dispatches to `private.transfer_apply_copy` or `private.transfer_apply_cheap`.
  - `transfer_apply_copy` writes new ids. In move mode it first snapshots the source rows, clears their late columns and deletes them children-first.
  - `transfer_apply_cheap` handles a move within the same company tree, for the whole customer, with no conflicts. It rewrites `tenant_id` in place with the composite FKs deferred, and writes one "transferred out" audit entry in the source.
  - Storage files are copied by the app after the commit. Then `public.transfer_check_files` reads `storage.objects` and sets `files_status`.

**Tech Stack:** Supabase (Postgres 15, PostgREST, generated RLS, CLI 2.9.6), pgTAP (`pnpm test:db`). Vue 3.5 + PrimeVue 4 + Tailwind, TanStack Query 5, pinia, vue-i18n, vitest 3 (happy-dom).

**Spec:** `docs/superpowers/specs/2026-11-03-moesa-panel-modules-design.md` §6 "M21 Kiracılar arası veri aktarımı" (its "Kenar durumları" rulings are binding). Also read:
- K1: `customer` is a plain table with composite `(x_id, tenant_id)` FKs.
- K5: codes are per tenant and never edited.
- K8: no sensitive fields.
- M19: the `media` row and its file are copied together. The path is `<tenant_id>/<media_id>/<file>` and the thumbnail is `<tenant_id>/<media_id>/thumb/thumb.webp`.
- M4: the polymorphic `document_entity`.

Conventions come from the latest plans in `docs/superpowers/plans/` (2026-11-04-phase2c…, 2026-11-05-m20…).

## Calls made here (spec silent or under-determined; controller rulings marked R)

1. **Signature (R5).** `public.transfer_customer(source_tenant UUID, target_tenant UUID, customer_id UUID, mode TEXT, decisions JSONB DEFAULT '{}', dry_run BOOLEAN DEFAULT TRUE, report_hash TEXT DEFAULT NULL, product_ids UUID[] DEFAULT NULL) RETURNS JSONB`. The spec's six parameters come first. `report_hash` carries the rehearsal's hash to the real run, and `product_ids` selects a product-only transfer.
2. **Deferred FKs instead of `ON UPDATE CASCADE` (R1).** A cascade cannot handle `product_supplier_fkey`, because the supplier never moves. Nor can it handle `customer_contract_document_fkey`, because the customer and its document reference each other. So the cheap path does this:
   - The 49 composite FKs between registry tables are made `DEFERRABLE INITIALLY IMMEDIATE` in place (Task 2).
   - It updates `tenant_id` table by table, then ends with `SET CONSTRAINTS ALL IMMEDIATE`.
   - Deferral covers the NO ACTION check on update only. **`ON DELETE RESTRICT` is checked at once even on a DEFERRABLE FK**, which is why the move delete clears the late columns first (Task 6).
3. **Permissions and ownership (R3).** "Management suffices" is checked on permissions, never on a role name. The caller needs:
   - `public.transfer` insert in both tenants;
   - select on every registry table in the source;
   - insert on every registry table in the target that has an insert permission.

   The transfer permissions go to the owner role and to every existing role holding `public.setting` update (management); the coordinator does not get them. Between two companies the caller must also **own the root company of each tree**. That is `private.owns_company(user_id, tenant_id)`: a `tenant_owner` row on `(SELECT e.company_id FROM private.entitlements(ARRAY[tenant_id]) e)`, not `owned_tenants`. A super admin passes.
4. **Customer and supplier `new_code` (R2).** These codes are typed by hand (`^[A-Z]{3}$`, `^[A-Z]{2}[0-9]{1,3}$`), so the decision carries `code`, which must be free in the target. Project, PO, SHP, CR and incident codes come from the target's counter (`private.next_code_in`). The child codes of a re-coded customer keep their old prefix.
5. **Move mode offers no `skip` (R5).** In a product-only move, any row outside the package that references a package product refuses the move with `transfer_product_in_use`. Such a row is a project link, a PO line, a market cell or a CR product line.
6. **Product-only transfers** never move or delete the customer row; it is mapped or copied like a supplier. Selected variants bring their parent product.
7. **Users rule.** A user is a member of the target when they have a `tenant_user` row there or `private.owns_company(user, target)` holds. For a non-member:
   - author columns (`created_by`, `uploaded_by`, `author_id`) become the caller;
   - assignment columns (`assignee_id`, `coordinator_id`, `owner_id`) become NULL;
   - decision records (`pi_checked_by`, `closed_by`, `company_approved_by`) are kept, since they are historical facts and the FK points to the global `public.user`.

   Non-members are reported but are not conflicts.
8. **Audit (R4).**
   - **Copy path.** The transfer row is the first write, so the target's audit transaction is about `transfer` (the "came by transfer" entry). Before the source deletions the function clears `audit.transaction_id`, so the deletions form their own audit transaction in the source. It then restores the target's.
   - **Cheap path.** It writes the target's `transfer` entry, plus one hand-written "transferred out" entry in the source. That entry is an `audit_transaction` with `table_name 'customer'`, `operation 'DELETE'` and `record_id` = the customer, and one `audit_log` row whose `old_data` is the customer row and whose `new_data` is `{"transferred_to": target, "transfer_id": id}`.
   - **Revert guard.** Every transaction id goes to `transfer.audit_transaction_ids`. `public.revert_audit_transaction` itself refuses (`audit_transfer_not_revertable`), before its loop, any of those transactions and any transaction with an `audit_log` row of `table_name 'transfer'`. That also covers the later `transfer_check_files` updates.
9. **Retry after the dialog closes.** The target customer's card shows a notice with "Retry file copy" while a transfer into it has `files_status <> 'done'`.
10. **Settings gaps.** One rule: `spec_sheet_required`. It is evaluated on the **source** product and the collected package. A product is listed when the target company's `spec_sheet_required_from` (`private.company_setting(target, …)`) is missing, unreadable or reached, or its status is `concept`, `development` or `approved`, **and** no package `document` of `type 'spec_sheet'` with `status 'signed'` names it. This mirrors `private.po_line_needs_spec`, whose product lookup cannot see the target. It is a warning, not a conflict.
11. **Gate validation.** For every package project, the function checks two things. The gate codes must equal `public.gates_for(type, path, packages)`, in the same positions. And no gate may be `passed` while a gate at a lower position is not `passed`. If either check fails, it refuses with `transfer_gate_invalid` (409), on the rehearsal and on the run. This replaces the guard that the flag skips.
12. **Storage files.** A `files` entry is `{media_id, from, to, keep_source}`. `keep_source` is TRUE for shared media, whose source row stays. After a `done` copy in move mode, the app removes only the `from` paths with `keep_source = FALSE`. `service_role` keeps its default INSERT on `public.transfer` by design (server-side tooling); only anon and authenticated are revoked.

## Review Focus

1. **Double submit or network retry of the real run.** After the first commit the target holds the codes and GTINs, so the report differs. Expected: the second call is refused with `transfer_report_stale` and nothing is written twice. Test: Task 5 "a second identical run is stale".
2. **A record changes between rehearsal and run.** Example: someone adds a contact in the source. Expected: the hash differs and the run is refused with `transfer_report_stale`. Test: Task 4 "a new contact makes the report stale".
3. **Frozen history in the target.** A passed gate, a closed incident and a project in a later phase arrive. Expected: G1 stays `passed` with its `passed_at`, its approval document follows, the incident stays `closed`, `current_phase` is unchanged, and no extra gates or checklist rows appear. Test: Task 6 "passed gates and closed incidents arrive as they were".
4. **A media row whose source file is missing** (an orphan). Expected: the transfer commits, `files_status` becomes `partial`, the path is listed in `missing_files`, and in move mode no source file is deleted. Tests: Task 8 "a missing source file leaves the transfer partial"; Task 9 "keeps the source files while the copy is partial".
5. **Reverting a transfer from the audit log**, including the file-check update the newest entry shows. Expected: refused with `audit_transfer_not_revertable`, and nothing is undone. Tests: Task 1 "a transfer's audit transactions cannot be reverted"; Task 8 "the file check cannot be reverted".
