# M21 Cross-Tenant Transfer (Kiracılar arası veri aktarımı): Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A user entitled in two tenants rehearses, then copies or moves a customer package (or selected products of one customer) from one tenant to the other in one database transaction. Afterwards the app copies the package's Storage files and records whether the copy finished.

**Architecture:**
- **Registry.** `private.transfer_registry` (a SQL table) lists every transferred table: its root, the registry table and column that scope its rows, the polymorphic `document_entity` value it answers to, its late (cyclic) columns, user columns and code kind, in insert order. The function is generic over it: each row is read as `jsonb`, its ids are rewritten through an id map, and it is written back with `jsonb_populate_record`. A pgTAP test fails when a table with a foreign key to a registry table is not registered.
- **Transfer flag.** `private.transferring()` is TRUE only while `moesa.transfer_id` names the `public.transfer` row inserted by the current transaction (`xact_id = pg_current_xact_id()`). A user cannot insert that row: authenticated has only SELECT on `public.transfer`. `private.rules_bypassed()` also accepts the flag. The trigger functions that would overwrite copied values, or refuse frozen rows, return at once under the flag. The integrity checks stay on.
- **One entry point.** `public.transfer_customer(...)` (SECURITY DEFINER) checks access and plans, collects the package into temp tables, and builds the report and its hash. With `dry_run` it returns the report. Otherwise it recomputes the report, compares the hash and the decisions, then dispatches to `private.transfer_apply_copy` (new ids; in move mode the source rows are snapshotted and deleted first, then written) or `private.transfer_apply_cheap` (same company tree, move, whole customer, no conflicts: `tenant_id` rewritten in place with the composite FKs deferred). Storage files are copied by the app after the commit, then `public.transfer_check_files` reads `storage.objects` and sets `files_status`.

**Tech Stack:** Supabase (Postgres 15, PostgREST, generated RLS, CLI 2.9.6), pgTAP (`pnpm test:db`). Vue 3.5 + PrimeVue 4 + Tailwind, TanStack Query 5, pinia, vue-i18n, vitest 3 (happy-dom).

**Spec:** `docs/superpowers/specs/2026-11-03-moesa-panel-modules-design.md` §6 "M21 Kiracılar arası veri aktarımı" (its "Kenar durumları" rulings are binding). Also read K1 (plain `customer`, composite `(x_id, tenant_id)` FKs), K5 (codes per tenant, never edited), K8 (no sensitive fields), M19 (`media` row + file copied together, path `<tenant_id>/<media_id>/<file>`) and M4 (polymorphic `document_entity`). Conventions come from the latest plans in `docs/superpowers/plans/` (2026-11-04-phase2c…, 2026-11-05-m20…).

## Calls made here (spec silent or under-determined; marked so a reviewer can overturn them)

1. **Signature.** `public.transfer_customer(source_tenant UUID, target_tenant UUID, customer_id UUID, mode TEXT, decisions JSONB DEFAULT '{}', dry_run BOOLEAN DEFAULT TRUE, report_hash TEXT DEFAULT NULL, product_ids UUID[] DEFAULT NULL) RETURNS JSONB`. The spec's six parameters come first. `report_hash` carries the rehearsal's hash to the real run. `product_ids` selects a product-only transfer.
2. **Deferred FKs instead of `ON UPDATE CASCADE`.** A cascade cannot handle `product_supplier_fkey`, because the supplier never moves and its row would be left in the source. It cannot handle `customer_contract_document_fkey` either: the customer and its document reference each other. So the cheap path makes the composite FKs between registry tables `DEFERRABLE INITIALLY IMMEDIATE`, updates `tenant_id` table by table in registry order and ends with `SET CONSTRAINTS ALL IMMEDIATE` inside the function. The exact 49 constraints are listed in Task 2.
3. **"management suffices"** is checked on permissions, never on a role name. The caller needs `public.transfer` insert in both tenants, select on every registry table in the source, and insert on every registry table in the target that has an insert permission. The migration grants `public.transfer` select/insert to the built-in owner role and to every existing role holding `public.setting` update (management). The coordinator does not get it. Between companies the caller must also own both tenants (`private.owned_tenants`); a super admin passes.
4. **Customer and supplier `new_code`.** There is no counter for these codes: they are typed (`^[A-Z]{3}$`, `^[A-Z]{2}[0-9]{1,3}$`). So the decision carries `code`, which must be free in the target. Project, PO, SHP, CR and incident codes come from the target's counter (`private.next_code_in`). The child codes of a re-coded customer keep their old prefix.
5. **Move mode offers no `skip`.** A skipped row would stay behind and block the deletion of its parents. In a product-only move, any row outside the package that references a package product refuses the move with `transfer_product_in_use`: a project link, a PO line, a market cell or a CR product line. The spec names only the project; the rule is the same.
6. **Product-only transfers** never move or delete the customer row; it is mapped or copied like a supplier. Selected variants bring their parent product.
7. **Users rule.** It applies when the user is not a member (`tenant_user`) or owner of the target. Author columns (`created_by`, `uploaded_by`, `author_id`) become the caller. Assignment columns (`assignee_id`, `coordinator_id`, `owner_id`) become NULL. Decision records (`pi_checked_by`, `closed_by`, `company_approved_by`) are kept, because they are historical facts and the FK is to the global `public.user`. Non-members are reported but are not conflicts, so they do not block the cheap path.
8. **Audit.** The transfer row is the first write, so the target's audit transaction is about `transfer` (the "came by transfer" entry). Before the source deletions the function clears `audit.transaction_id`, so the deletions form their own audit transaction in the source. Then it restores the target's. Both ids go to `transfer.audit_transaction_ids`, and reverting either is refused (`audit_transfer_not_revertable`). The cheap path writes UPDATEs only; they are logged in the target's transaction, and the source's audit feed shows nothing for them.
9. **Retry after the dialog closes.** The target customer's card shows a notice with "Retry file copy" while a transfer into it has `files_status <> 'done'`. There is no transfer list page.
10. **Settings gaps** reported in this version: one rule. The product would need a spec sheet in the target (`private.po_line_needs_spec(product, target)`) and has no signed one. It is a warning, not a conflict.

## Review Focus

1. **Double submit / network retry of the real run.** After the first commit the target holds the customer code and the GTINs, so the second call's report differs. Expected: the second call is refused with `transfer_report_stale` and nothing is written twice. Test: Task 5 "a second identical run is stale".
2. **A record changes between rehearsal and run** (someone adds a contact in the source). Expected: the counts differ, the hash differs, and the run is refused with `transfer_report_stale`. Test: Task 4 "a new contact makes the report stale".
3. **Frozen history in the target.** A passed gate, a closed incident and a project in a later phase arrive unchanged. Expected: G1 stays `passed` with its `passed_at`, the incident stays `closed`, `current_phase` is unchanged and no extra gates or checklist rows are created. Test: Task 6 "passed gates and closed incidents arrive as they were".
4. **A media row whose source file is missing** (an orphan). Expected: the transfer commits, `files_status` becomes `partial`, the path is listed in `missing_files`, and in move mode the other source files are not deleted. Tests: Task 8 "a missing source file leaves the transfer partial", and Task 9 "keeps the source files while the copy is partial".
5. **Reverting a transfer from the audit log** (the revert button is shown for every row). Expected: refused with `audit_transfer_not_revertable`, nothing undone. Test: Task 1 "a transfer's audit transactions cannot be reverted".
